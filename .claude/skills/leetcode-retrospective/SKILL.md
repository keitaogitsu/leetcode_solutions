# LeetCode 振り返りの書き足し

解答ファイルに、あとで見返して復習できるメモをコメントで残す。
コードを書くのは本人で、このスキルはコードを書き換えない。書くのはコメントだけ。

## なぜ書くか

解けた直後は、何を間違えて何に気づいたかをいちばんよく覚えている。
後から読み返せるのは、「最終版がなぜ正しいか」と「最初のコードがどこでなぜ動かなかったか」の2点。
この2点を残すと、同じ種類の問題で同じ失敗を繰り返しにくくなる。

## 手順

1. 対象ファイルを読む。同じディレクトリにある、書き足し済みのファイル(例 `14.longest-common-prefix.py`)があれば、それも読んで書式を合わせる。
2. 現在の解答(`@lc code=start` 〜 `@lc code=end`)を、最終版として扱う。
   - 正しく動くか不安なら、落ちそうな入力(空、1要素、重複、境界)を頭の中か実行で確認する。
   - 最終版のバグを見つけたら、メモを書く前に本人へ伝える。
3. 古いコードがファイル内にあれば、それが「最初に書いたコード」。
   なければ、会話の中で最初に書かれたコードを使う。履歴に残っていなければ本人に聞く。
4. 次の順で、コメントを書き足す。

### ファイルの構成

```
(lc code=start 〜 lc code=end)
# --- 最終版の考え方と手順 ---
# --- 最初に書いたコード(動かない版) ---   ← 古いコードをコメントアウトして残す
# --- 最初のコードの振り返り ---
```

### 最終版の考え方と手順

- 【考え方】: 問題の構造と、なぜこの解法(データ構造やアルゴリズム)が合うのかを2〜3行で書く。
- 【手順】: 番号付きで、コードの流れを追えるように書く。コードの行と対応させる。

### 最初のコードの振り返り

- 【いい点】: 方針や構造で、最終版につながったものを具体的に書く。お世辞は書かない。
- 【ダメな点 → 直し方】: 番号を付け、各項目を「何が起きるか → どう直すか」の形にする。
  - 実際にその入力でどうなるかを書く(例: `"()"` が False になる)。
  - 原因が複数ある時は、分けて書く。たとえば「対応のバグ」と「方針そのものの限界」は別の項目にする。
- 【途中で詰まった点】: 最初のコードのあとに、書き直しの途中で詰まったことがあれば書く。なければ省く。
- 【学んだこと】: 次の問題にも使える一般化した教訓を2〜3個書く。

## 書くときの注意

- 事実は実際の挙動で確かめて書く。推測で「こうなるはず」と書かない。会話中に自分が間違った説明をしていたことに気づいたら、メモに書く前に訂正してから書く。
- コードは既存のものを残す。書き換えるのはコメント部分だけ。古いコードは消さず、コメントアウトして残す。
- 追記は `@lc code=end` の直後と、ファイル末尾に分ける。既存のコメントがあれば、重複させず更新する。
- 日本語で、箇条書き中心に短く書く。教科書のような説明は避ける。
- 書き終えたら、どこに何を足したかを2〜3行で伝える。コードを実行して確認していなければ、そう明記する。
